## Context

Products live in the `products` table (`active`, `sort`, price in fen) and can only be changed with SQL. There is no admin surface and no account system (accounts were removed on request). Orders are settled only by provider confirmation through `fulfilOrder`; a mispaid USDT order cannot be recovered.

## Proposal

1. **Admin API** (`modules/admin/`), under `/api/admin`, enabled only when `ADMIN_TOKEN` (at least 16 characters) is set; otherwise every admin route answers 404. Bearer token, compared in constant time.
   - `GET /session` - token check.
   - `GET /products`, `POST /products`, `PATCH /products/:id` - all products including unlisted ones. No delete: orders reference products, so a product is unlisted instead.
   - `GET /orders` - paginated, filter by status, search by order number or email, with issued keys.
   - `POST /orders/:orderNo/settle` - settle an unpaid order by hand through `fulfilOrder`.
2. **Admin app** `apps/admin` (`@cdk/admin`): same stack and gates as the other SPAs, zh-CN, static `dist`. Token sign-in kept in `sessionStorage`; `/` products (table, create/edit form, list/unlist toggle), `/orders` (filter, search, pagination, keys, manual settle with confirmation). Build-time env `VITE_API_URL`.
3. **Tooling/docs**: nsl name `cdk-admin`, root `dev` / `build` scripts, `.env.example`, README, architecture, changelog.

Tests first: admin routes 404 without a configured token and 401 with a wrong one; product create / edit / unlist reflected in the shop catalog; validation; order filter and search; manual settle issues keys once; component tests for product editing and order settlement.

## Risks

- The admin token is a single shared secret with full control over prices and free key issuance; it must be long, random and sent over HTTPS only. There is no audit trail of who did what.
- Manual settlement issues keys without payment by design.
- No rate limiting on token attempts; a long random token is the only defence.

## Scope

New `apps/admin`, new `modules/admin`, config, shared contracts, order serialisation shared between shop and admin, scripts, tests, docs. No migration.

## Alternatives

- Admin pages inside the dashboard or shop: contradicts separate deployment and exposes admin code to buyers.
- Admin accounts with passwords and roles: more than a single operator needs.

## Annotations

User: add an admin page, deployed independently of the shop and the dashboard.
